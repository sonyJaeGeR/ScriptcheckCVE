# ScriptcheckCVE — проверка CVE-2026-98432 в ядре Linux

**Локальный Bash-скрипт для оценки статуса CVE-2026-98432 на работающем ядре Linux.** Предназначен прежде всего для инвентаризации и предварительной проверки серверов, включая production-системы на **Astra Linux**, Debian и Ubuntu.

> [!IMPORTANT]
> Скрипт выполняет **диагностику в режиме read-only**. Он не эксплуатирует CVE, не обновляет ядро, не перезагружает сервер, не меняет параметры `sysctl` и не добавляет правила межсетевого экрана. Его результат — техническая оценка по доступным свидетельствам, **не доказательство отсутствия уязвимости во всех случаях**.

**Проверяемая ревизия:** `check-cve-2026-98432-prod-astra.sh`, v3.1 от 02.11.2026. Информация о фиксированных версиях и статусах производителей актуальна только на дату, указанную в коде, и может измениться после публикации новых обновлений.

## 1. О CVE-2026-98432

**CVE-2026-98432** — уязвимость *use-after-free* (UAF) в сетевой подсистеме IPv4 ядра Linux при обработке TCP-запросов на установление соединения. Проблема связана с временем жизни структур, хранящих IPv4 Options, и параллельной обработкой повторного SYN либо миграции request socket.

Упрощённо механизм выглядит так:

1. При установлении TCP-соединения ядро обрабатывает IPv4 Options из входящего запроса.
2. Один поток выполнения может передать указатель на эти опции дочернему сокету, а другой — продолжать использовать его для формирования ответа SYN-ACK.
3. При определённой последовательности событий память освобождается до завершения чтения.
4. Последующее обращение к освобождённой памяти приводит к UAF, потенциально вызывая сбой ядра, повреждение памяти и другие последствия. Возможность удалённой эксплуатации зависит от условий и конфигурации.

Исправление в upstream связано с корректным освобождением памяти после *RCU grace period* (`kfree_rcu()`), чтобы параллельные читатели успели завершить доступ.

Уязвимость затрагивает прежде всего обработку **IPv4/TCP**. Настройки MPTCP могут менять поверхность атаки, но отключённый MPTCP **не означает**, что уязвимость устранена: путь с повторным SYN существует отдельно. Наличие открытого TCP-порта также не является доказательством эксплуатации или уязвимого кода.

**Базовые ссылки:** [объявление Linux kernel CVE team](https://lists.openwall.net/linux-cve-announce/2026/10/15/1), [карточка CVE](https://www.cve.org/CVERecord?id=CVE-2026-98432), [бюллетень Red Hat](https://access.redhat.com/security/vulnerabilities/RHSB-2026-016).

## 2. Возможности и ограничения

Скрипт:

- определяет дистрибутив и **фактически запущенное ядро** через `uname`;
- обнаруживает Astra Linux и читает её сведения о версии и сборке;
- пытается установить точный бинарный пакет работающего ядра и, где возможно, соответствующий **исходный пакет**;
- для Debian использует встроенные пороги исправления, привязанные к выпуску, исходному пакету и линейке версии;
- для Debian/Ubuntu по запросу получает запись **OSV** и анализирует версию исходного пакета в контексте конкретного выпуска дистрибутива;
- поддерживает отдельный режим проверки заведомо **немодифицированного upstream-ядра**;
- выявляет признаки обновления образа ядра или метаданных пакета **после загрузки**;
- обнаруживает некоторые активные livepatch через `/sys/kernel/livepatch`;
- считывает `net.mptcp.enabled`, `net.ipv4.tcp_migrate_req` и количество локально слушающих TCP/MPTCP-сокетов;
- возвращает статус `PATCHED`, `NOT_AFFECTED`, `VULNERABLE` либо `UNKNOWN` и соответствующий код завершения.

**Скрипт не:**

- отправляет сетевые пакеты для эксплуатации CVE;
- выполняет PoC или проверку UAF в памяти ядра;
- определяет уязвимость по открытым портам;
- устанавливает обновления и livepatch;
- проверяет содержимое работающего ядра побайтово;
- вносит изменения в настройки сети или ОС;
- подтверждает, что внешние межсетевые экраны реально блокируют IPv4 Options;
- автоматически подтверждает исправление на Astra Linux по версиям Debian/Ubuntu или upstream;
- гарантирует достоверный результат для произвольного вендорского ядра.

## 3. Поддерживаемые системы

| Система | Определение пакета | Основание для вердикта |
|---|---|---|
| **Astra Linux 1.6 / 1.7 / 1.8** | `dpkg`, `/etc/astra_version`, `/etc/astra/build_version` | Диагностика ядра и компенсирующих настроек; без подтверждённого порога исправления результат `UNKNOWN` |
| **Debian 12 / 13 / 14** | `dpkg-query`, исходный пакет | Встроенные пороги для известных веток; дополнительно OSV через `--online` или `--osv-file` |
| **Ubuntu** | `dpkg-query`, сопоставление пакета подписанного образа с пакетом модулей | OSV при наличии данных для точного выпуска и исходного пакета; иначе `UNKNOWN` |
| **RHEL-подобные / RPM-дистрибутивы** | `rpm` | Сведения о пакете и changelog; автоматический вендорский вердикт по RPM-бюллетеням **не реализован** |
| **Arch-подобные** | `pacman` | Сведения о пакете; upstream-оценка только с явным `--upstream` и подтверждением происхождения сборки |
| **Другие Linux** | По доступным утилитам | В общем случае `UNKNOWN`, если нельзя получить надёжное свидетельство исправления |

**Важно:** таблица описывает реализованные механизмы, а не полный список официально поддерживаемых версий дистрибутивов. Внутри контейнера оценивается не пакет хостового ядра, поэтому итоговый вердикт принудительно становится `UNKNOWN`.

## 4. Требования

Обязательно:

- Linux;
- **Bash** (не `/bin/sh`);
- доступ для чтения стандартных системных сведений (`/proc/stat`, `/etc/os-release`, `uname`);
- стандартные системные утилиты, используемые скриптом: `uname`, `awk`, `sort` с поддержкой `-V`, `head`, `stat` и др.

Дополнительные утилиты используются **при наличии**:

- `dpkg-query` / `dpkg` — Debian, Ubuntu, Astra;
- `rpm` — RPM-дистрибутивы;
- `pacman` — Arch-подобные системы;
- `sysctl` — чтение сетевых параметров;
- `ss` — сведения о слушающих сокетах;
- `gzip` — поиск упоминаний в changelog;
- `systemd-detect-virt` — определение контейнера;
- `python3` — разбор JSON OSV для `--online` и `--osv-file`;
- доступ по HTTPS к `api.osv.dev` — **только для `--online` на Debian/Ubuntu**, когда удалось определить исходный пакет.

**Права root не требуются.** При ограничениях доступа отдельные диагностические поля могут быть недоступны; это не превращается автоматически в статус `VULNERABLE`.

## 5. Установка и запуск

### 5.1. Получение исходного кода

Склонировать репозиторий:

```bash
git clone https://github.com/sonyJaeGeR/ScriptcheckCVE.git
cd ScriptcheckCVE
```

Рекомендуется **просмотреть содержимое файла до запуска**, особенно на production-серверах:

```bash
less check-cve-2026-98432-prod-astra.sh
bash -n check-cve-2026-98432-prod-astra.sh
```

### 5.2. Обычная офлайн-проверка — рекомендуется для production

```bash
bash check-cve-2026-98432-prod-astra.sh
```

Без параметров скрипт **не инициирует сетевых запросов** и ничего не меняет в ОС. В частности, он не выполняет ни `reboot`, ни `apt upgrade`, ни `sysctl -w`.

### 5.3. Сбор вывода для отчёта ИБ

Создать лог в текущем каталоге **на стороне оператора** (это запись, созданная перенаправлением оболочки, а не самим скриптом):

```bash
bash check-cve-2026-98432-prod-astra.sh > cve-2026-98432-report.log 2>&1
status=$?
printf 'Код завершения: %s\n' "$status"
cat cve-2026-98432-report.log
```

Скрипт намеренно использует ненулевые коды завершения для `VULNERABLE` и `UNKNOWN`; поэтому ненулевой код сам по себе **не означает ошибку выполнения**.

### 5.4. Онлайн-проверка Debian/Ubuntu по OSV

```bash
bash check-cve-2026-98432-prod-astra.sh --online
```

Используется HTTPS-запрос к `https://api.osv.dev/v1/vulns/DEBIAN-CVE-2026-98432` либо `https://api.osv.dev/v1/vulns/UBUNTU-CVE-2026-98432`.

В запросе передаётся **идентификатор записи CVE**, но не имя сервера, `uname -r` или локальная версия пакета. Вместе с тем сервис и сетевые посредники могут видеть обычные сетевые метаданные соединения, включая исходный IP-адрес. На Astra этот режим **не выполняет OSV-запрос**, так как сведения Debian/Ubuntu нельзя переносить на ядра Astra.

### 5.5. Офлайн-проверка по заранее скачанному бюллетеню OSV

На машине с доступом к интернету можно получить JSON для Debian:

```bash
curl -fL --retry 2 -o DEBIAN-CVE-2026-98432.json \
  https://api.osv.dev/v1/vulns/DEBIAN-CVE-2026-98432
```

После переноса JSON в текущий каталог проверяемого Debian-хоста:

```bash
bash check-cve-2026-98432-prod-astra.sh --osv-file DEBIAN-CVE-2026-98432.json
```

Аналогично для Ubuntu используется файл `UBUNTU-CVE-2026-98432.json` с записью `UBUNTU-CVE-2026-98432`. Скрипт сверяет ID записи внутри JSON; подмена Debian-бюллетеня Ubuntu-бюллетенем не должна приводить к корректному вендорскому результату. Этот режим **не является проверкой Astra**.

### 5.6. Самопроверка логики

```bash
bash check-cve-2026-98432-prod-astra.sh --self-test
```

Ожидаемая строка для проверяемой ревизии:

```text
SELF TEST OK: 25 upstream cases + 4 Astra branch cases
```

### 5.7. Проверка оригинального upstream-ядра

```bash
bash check-cve-2026-98432-prod-astra.sh --upstream
```

> [!CAUTION]
> **Не используйте `--upstream` для обычных ядер Astra, Debian, Ubuntu, RHEL и других вендоров.** Параметр **не проверяет сам**, что ядро собрано без патчей и backport-изменений: он означает, что оператор **уже достоверно установил** происхождение запущенной сборки. На Astra Linux параметр явно запрещён скриптом.

| Параметр | Назначение |
|---|---|
| Без параметров | Офлайн read-only проверка |

## 7. Как работает скрипт

### Шаг 1. Определяет работающую систему

Считываются:

- `uname -s`, `uname -r`, `uname -v`;
- `/etc/os-release` — имя, ID, версия и семейство дистрибутива;
- `/proc/stat` (`btime`) — приблизительное время последней загрузки;
- для Astra — `/etc/astra_version` и `/etc/astra/build_version`;
- для Ubuntu, если доступно, — `/proc/version_signature`.

**Почему:** обновлённый пакет на диске ещё не означает, что сервер уже использует исправленное ядро. Основной объект оценки — **работающее ядро**.

### Шаг 2. Проверяет, не является ли система контейнером

Скрипт использует `systemd-detect-virt --container` и признаки `/.dockerenv` / `/run/.containerenv`.

**Почему:** внутри контейнера команда `uname -r` показывает ядро **хоста**, а база `dpkg` / `rpm` / `pacman` может относиться к образу **контейнера**. Делать вывод о защищённости хоста по пакетам контейнера некорректно. Поэтому итог — `UNKNOWN`.

### Шаг 3. Связывает ядро с пакетом

Для Debian-подобных систем:

1. Ищет установленный `linux-image-$(uname -r)` или `linux-image-unsigned-$(uname -r)`.
2. Если пакет не найден, проверяет владельца `/boot/vmlinuz-$(uname -r)` через `dpkg-query -S`.
3. Для Astra дополнительно может проверить владельца файлов `modules.order` и `modules.builtin` в каталоге `/lib/modules/$(uname -r)` (или `/usr/lib/modules/...`).
4. Получает бинарную и исходную версии пакета через `dpkg-query`.

У Ubuntu подписанный образ ядра нередко собран из `linux-signed`, а сведения об уязвимости относятся к исходному пакету самого ядра (`linux`, `linux-aws`, `linux-azure` и т. п.). Скрипт пробует сопоставить подписанный образ и пакет модулей/заголовков **только при совпадении их версий**, после чего использует соответствующий исходный пакет.

Для RPM-систем определяется владелец файла образа ядра; для Arch-подобных систем — `pkgbase` и версия установленного пакета.

**Почему:** проверка только строки `uname -r` даёт ложные результаты для backport-исправлений. У производителя исправление может быть внесено в пакет со старой upstream-версией.

### Шаг 4. Ищет признаки смены ядра после запуска

Сравнивает время загрузки с временем изменения `/boot/vmlinuz-...` и, если возможно, метаданных установленного пакета (`/var/lib/dpkg/info/*.list`, `RPM INSTALLTIME`). Для Ubuntu учитывает и сопоставленный пакет модулей.

**Почему:** если файл образа или пакет изменился после загрузки, нельзя уверенно отождествить его с кодом, выполняющимся сейчас. При наличии такого признака любой положительный или отрицательный вердикт, основанный на пакете, переводится в `UNKNOWN`.

Это **эвристика**, а не полноценная проверка цепочки загрузки: неизменный timestamp не доказывает побайтового совпадения запущенного ядра и пакета на диске.

### Шаг 5. Собирает сведения об исправлениях

**5.1. Debian — встроенный офлайн-снимок от 02.11.2026.**

Порог применяется **только** при совпадении выпуска Debian, имени **исходного** пакета и ожидаемой линейки исходной версии.

| Выпуск | Исходный пакет | Ожидаемая ветка | Порог исправления в скрипте |
|---|---|---|---|
| Debian 12 | `linux` | `6.1.*` | `6.1.190-1` |
| Debian 12 | `linux-6.12` | `6.12.*` | `6.12.113-1~deb12u1` |
| Debian 13 | `linux` | `6.12.*` | `6.12.113-1` |
| Debian 14 | `linux` | `7.2.*` | `7.2.10-1` |

Для сравнения используется `dpkg --compare-versions`, а не обычное сравнение строк. Если исходный пакет или ветка не совпали, встроенный порог **не используется**. Порог — снимок данных на указанную дату; для новых веток и исправлений требуется актуальный бюллетень [Debian Security Tracker](https://security-tracker.debian.org/tracker/CVE-2026-98432).

**5.2. Debian / Ubuntu — OSV (`--online` или `--osv-file`).**

Скрипт использует JSON с идентификатором `DEBIAN-CVE-2026-98432` либо `UBUNTU-CVE-2026-98432` и проверяет:

- соответствует ли ID ожидаемому;
- не отозвана ли запись;
- совпадают ли экосистема и выпуск дистрибутива;
- совпадает ли **имя исходного пакета**;
- попадает ли установленная версия в диапазоны `introduced`, `fixed`, `last_affected` или `limit`, либо в список явных версий.

Для сравнения версий применяется `dpkg --compare-versions`; JSON разбирается с помощью стандартной библиотеки Python. На получение OSV установлен тайм-аут **12 секунд**, максимальный размер ответа — **20 МБ**. При ошибке загрузки, несовпадении источника или неоднозначных данных результат этого источника — `UNKNOWN`.

**5.3. Upstream (`--upstream`).**

Сравнение версий допустимо **только для подтверждённого немодифицированного upstream-ядра**. В ревизии v3.1 заложены следующие ориентиры:

| Ветка | Первая исправленная upstream-версия |
|---|---|
| `5.10` | `5.10.272` |
| `5.15` | `5.15.223` |
| `6.1` | `6.1.190` |
| `6.6` | `6.6.159` |
| `6.12` | `6.12.113` |
| `6.18` | `6.18.56` |
| `7.2` | `7.2.10` |
| `7.3` | `7.3-rc7` и позднее |

Для других веток применяется логика, реализованная в `upstream_verdict()`. Список отражает текущие правила **конкретной версии скрипта**, а не универсальную базу исправлений на все будущие релизы. Upstream-релизы, границы и backport-исправления нужно перепроверять по [Linux kernel CVE announcement](https://lists.openwall.net/linux-cve-announce/2026/10/15/1).

**5.4. Changelog.**

Скрипт ищет `CVE-2026-98432` или текст исправления в установленном changelog. Этот факт **только информационный**: упоминание CVE не всегда означает исправление, а отсутствие упоминания не доказывает уязвимость.

### Шаг 6. Учитывает livepatch

Проверяет файлы `/sys/kernel/livepatch/*/enabled`.

- Если найден активный livepatch, скрипт отражает это в отчёте.
- Если одновременно версия ядра указывает на `VULNERABLE`, итог становится `UNKNOWN`, потому что покрытие **конкретно этой CVE** не проверено.
- Если активный livepatch не обнаружен, это **не гарантия**, что другие механизмы динамического исправления отсутствуют.

### Шаг 7. Считывает сетевой контекст

Используются исключительно операции чтения:

```bash
sysctl -n net.mptcp.enabled
sysctl -n net.ipv4.tcp_migrate_req
ss -H -lnt4
ss -H -lnM
```

Скрипт показывает значения двух параметров, количество локально слушающих IPv4 TCP-сокетов и MPTCP-сокетов (если `ss` поддерживает соответствующий режим).

**Почему это отдельный раздел `Exposure`:** эти сведения полезны для оценки потенциальной поверхности атаки и временных мер, но не подтверждают и не исключают наличие UAF в ядре. Слушающий сокет может быть доступен только локально или из ограниченного сегмента. Состояние внешних маршрутизаторов и межсетевых экранов скрипту неизвестно.

### Шаг 8. Формирует вердикт

Алгоритм в общих чертах:

```text
Сведения о работающем ядре
           |
           v
Определение дистрибутива и пакета ядра
           |
           v
Наличие точных сведений производителя?
           |
           +-- Debian: встроенные пороги исправлений
           +-- Debian/Ubuntu: OSV (если запрошено)
           +-- Upstream: только при явном --upstream
           |
           v
Согласуются ли все доступные свидетельства?
           |
           +-- Нет --------------------> UNKNOWN
           |
           v
Не обнаружены ли контейнер / смена пакета после запуска?
           |
           +-- Есть сомнения ----------> UNKNOWN
           |
           v
Не меняет ли livepatch оценку VULNERABLE?
           |
           +-- Меняет -----------------> UNKNOWN
           |
           v
PATCHED / NOT_AFFECTED / VULNERABLE / UNKNOWN
```

При конфликте офлайн-данных Debian и записи OSV скрипт **не выбирает удобный ответ**, а возвращает `UNKNOWN`. Для Astra любой неподтверждённый build-specific вердикт остаётся `UNKNOWN`.

## 8. Особенности Astra Linux

**Astra Linux обрабатывается отдельно от Debian**, даже если в `/etc/os-release` присутствует `ID_LIKE=debian`.

Скрипт распознаёт Astra по ID дистрибутива, названию и/или наличию `/etc/astra_version`. Он считывает фактический релиз, определяет ветку **1.6 / 1.7 / 1.8**, пытается получить исходный пакет и его версию, а также проверяет два параметра:

- `net.mptcp.enabled`;
- `net.ipv4.tcp_migrate_req`.

Значения в отчёте интерпретируются так:

| Строка отчёта | Смысл |
|---|---|
| `BOTH DISABLED` | Оба параметра равны `0`; часть потенциальных путей атаки ограничена |
| `RECOMMENDED SETTINGS NOT FULLY APPLIED` | Хотя бы один параметр не равен `0`; требуется отдельная оценка необходимости временных мер |
| `INCOMPLETE DATA` | Не удалось считать один или оба параметра |
| `VENDOR_FIX_NOT_CONFIRMED` | Нет подтверждённого порога исправленного пакета Astra для используемой сборки |
| `POTENTIALLY_VULNERABLE` | **Рекомендация для учёта риска**, не итоговый машинный вердикт |

**Это не команды на изменение настроек.** Скрипт ничего не выключает. Любые изменения на production должны проходить отдельную проверку совместимости и регламент управления изменениями.

Если для используемой сборки Astra нет достоверного сведения об исправлении, итог:

```text
== VERDICT: UNKNOWN
```

Даже если оба параметра равны `0`, вердикт **не превращается в `PATCHED`**: остаётся сценарий с повторным SYN, а свойства реально запущенного ядра не подтверждены. В скрипте используется **датированная справочная информация по Astra (31.10–01.11.2026)**, а не автоматическая проверка свежих бюллетеней. Актуальные исправления необходимо сверять по [бюллетеням безопасности Astra](https://astra.ru/support/security-bulletins/) и документации производителя.

## 9. Расшифровка результатов

Финальный блок выглядит так:

```text
== VERDICT: UNKNOWN
Reason: no trustworthy fixed/affected evidence for the exact running build
Action: validate exact running kernel package against vendor advisory; review interim exposure without modifying production.
```

Это **пример формата**, а не заключение по конкретному серверу.

| `VERDICT` | Что означает | Как использовать в ИБ-процессе |
|---|---|---|
| `PATCHED` | По применённому источнику для идентифицированной сборки есть свидетельство исправления | Проверить происхождение сборки и совпадение с фактически загруженным ядром перед закрытием CVE |
| `NOT_AFFECTED` | В рамках реализованной проверки upstream-ядро старше точки появления проблемы | Проверить правомерность режима `--upstream` |
| `VULNERABLE` | Доступные корректные данные указывают на уязвимую версию/диапазон | Зарегистрировать уязвимость; меры изменения системы согласовывать отдельно |
| `UNKNOWN` | Доказательств недостаточно, они противоречат друг другу или неприменимы к системе | **Не считать исправленной и не утверждать подтверждённую эксплуатационную уязвимость** без дополнительной проверки |

В итоговом выводе есть и другие строки — `Vendor`, `Upstream`, `Changelog`, `Livepatch`, `Exposure`. **Их нельзя путать с финальным `VERDICT`.** Например, `BOTH DISABLED` говорит только о текущем значении двух `sysctl`, а `POTENTIALLY_VULNERABLE` — о необходимости учёта риска на Astra.

## 10. Коды завершения и автоматизация

| Код | Условие |
|---:|---|
| `0` | `PATCHED`, `NOT_AFFECTED`, а также успешный `--help` или `--self-test` |
| `1` | `VULNERABLE` |
| `2` | `UNKNOWN` |
| `3` | Ошибка аргументов, неподдерживаемая среда либо неуспешный self-test |

Пример безопасного использования в оболочке при проверке с передачей результата в систему учёта:

```bash
bash check-cve-2026-98432-prod-astra.sh
status=$?
case "$status" in
  0) echo 'Исправлено или не затронуто согласно свидетельствам скрипта' ;;
  1) echo 'Есть свидетельства наличия уязвимости' ;;
  2) echo 'Статус не определён — требуется ручная проверка' ;;
  3) echo 'Ошибка запуска или самопроверки' ;;
esac
```

**Не используйте один лишь код `0` для автоматического закрытия CVE** без анализа `VERDICT`, `Reason` и происхождения ядра. На некоторых сценариях код `0` означает `NOT_AFFECTED`, а не `PATCHED`.

## 11. Безопасность при запуске на production

В обычном режиме скрипт:

- выполняет чтение файлов `/etc`, `/proc`, `/sys`, `/boot` и метаданных пакетов;
- запускает штатные утилиты получения информации о системе;
- не требует root и не меняет конфигурацию;
- **не выполняет** `apt`, `dnf`, `yum` или другие операции установки;
- **не требует перезагрузки** и не вызывает её;
- не применяет правила фильтрации трафика;
- не отправляет данные в сеть без `--online`.

Влияние на сервер ожидается небольшим: несколько коротких команд, обращения к базе пакетов и чтение локальных сокетов. Однако «read-only» **не означает нулевую нагрузку**: любая диагностика использует CPU и I/O. Перед массовым запуском стоит проверить время выполнения на типовых хостах.

Рекомендации для производственной среды:

1. Запускать по умолчанию **без `--online`** и без `sudo`.
2. Проверить файл и зафиксировать ревизию Git, с которой выполняется аудит.
3. Не использовать `--upstream` для вендорских ядер.
4. Для Astra сохранять значения настроек и сведения о пакете вместе с результатом `UNKNOWN`.
5. При необходимости менять MPTCP, параметры миграции, firewall или ядро — проводить это **отдельной процедурой**, вне данного скрипта.
6. Не путать «нет внешней сетевой доступности» и «уязвимость устранена».

## 12. Известные ограничения и возможные ошибки оценки

1. **Снимки данных устаревают.** Пороги Debian и upstream захардкожены в v3.1; изменения бюллетеней требуют обновления кода или применения свежей OSV-записи.
2. **Astra не имеет автоматического сопоставления с вендорскими бюллетенями.** На 02.11.2026 скрипт не располагает проверенным перечнем исправленных сборок Astra; `UNKNOWN` здесь ожидаем.
3. **OSV — зависимость от полноты данных.** Отсутствие записи об исходном пакете не доказывает его безопасность, а интервалы в базе могут быть неполными или запаздывать.
4. **Привязка работающего ядра к установленному пакету не криптографическая.** Проверка временных меток помогает отсеять часть случаев обновления после загрузки, но не доказывает идентичность кода в памяти и файла на диске.
5. **Livepatch проверяется неполно.** Наличие `/sys/kernel/livepatch` не подтверждает, что конкретная CVE устранена. Отсутствие записи не исключает иных реализаций hotpatch.
6. **В контейнере оценивается хостовое ядро.** Пакеты контейнера обычно не описывают его; скрипт возвращает `UNKNOWN`.
7. **`--upstream` зависит от правильности утверждения оператора.** Скрипт не проверяет самостоятельно отсутствие backport-патчей, дополнительных коммитов или модификаций ядра.
8. **Сетевая экспозиция не проверяется извне.** Количество слушающих сокетов не учитывает ACL, сегментацию, балансировщики, внешний firewall и реальные маршруты атакующего.
9. **Возможны ограничения окружения.** Недоступные бинарники, нестандартная раскладка `/boot`, отсутствие владельца пакета или отсутствие Python для OSV приводят к сокращению доказательной базы.
10. **Статус не равен результату эксплуатации.** `VULNERABLE` означает уязвимый пакет/диапазон по доступным данным, а не то, что PoC сработает. `PATCHED` означает совпадение с оценкой исправления, но не абсолютную гарантию безопасности.

**Вывод:** при сомнении правильное поведение инструмента — `UNKNOWN`, а не ложный `PATCHED` или `VULNERABLE`.

## 13. Диагностика проблем

### `VERDICT: UNKNOWN` на Astra

Ожидаемо, когда нет подтверждения исправления **конкретного ядра Astra**. Проверьте строки `Astra release`, `Running kernel`, `Installed binary`, `Kernel source`, `Astra assessment` и соответствующий бюллетень производителя. Отсутствие подтверждённой исправленной версии не доказывает отсутствие исправления.

### `VERDICT: UNKNOWN` в Docker или другом контейнере

Ожидаемо: `uname` показывает хостовое ядро, а локальные пакеты — содержимое контейнера. Проверку необходимо выполнять **на самом Linux-хосте**, если для этого есть разрешённый доступ.

### `No corresponding installed kernel package could be established`

Возможные причины: нестандартное ядро, удалённый старый пакет после обновления, нестандартный путь `/boot`, недостаточные права чтения или нестандартный пакетный менеджер. Отсутствие пакета не является доказательством уязвимости.

### `kernel image changed after boot` / `kernel package metadata changed after boot`

На диске видны изменения после старта системы. Скрипт **не инициирует перезагрузку**. Итоговый статус может стать `UNKNOWN`, поскольку текущий пакет не обязательно совпадает с кодом уже работающего ядра.

### `Vendor (online/local OSV): UNKNOWN`

Возможные причины: недоступен `api.osv.dev`, нет Python 3, не удалось определить исходный пакет, данные OSV не совпали с дистрибутивом/пакетом или ответ оказался некорректным. Это не равнозначно `VULNERABLE`.

### `net.mptcp.enabled = unavailable`

Параметр может отсутствовать в конкретном ядре, быть недоступным для чтения или утилита `sysctl` может отсутствовать. Статус CVE из одного этого признака не выводится.

### Ошибка `--upstream cannot be used on Astra Linux vendor kernels`

Это предусмотренный запрет. Для Astra запускайте обычную офлайн-диагностику без `--upstream`.
